# 엔진별 선택과 구현 기준

## Phaser 2D

- Scene은 화면과 자원 수명 관리에 사용하고 경제/전투/인벤토리 규칙은 렌더링과 분리해 테스트 가능하게 만든다. 물리 엔진 내부를 무리하게 수동 step하지 말고 사용 중인 버전에 맞는 테스트 시계를 설계한다.
- 터치와 키보드는 같은 게임 명령으로 연결한다. 입력 이벤트 중복 등록을 막고 Scene shutdown 시 타이머·리스너·풀·진단 참조를 정리한다.
- 이미지 생성, generate2dsprite, generate2dmap 등 사용 가능한 전문 스킬로 일관된 에셋을 만든다. 컨셉 이미지를 충돌 맵으로 바로 취급하지 말고 화면 표시와 충돌/이동 가능 영역을 구분한다.
- 픽셀 아트라면 픽셀 스케일, 필터, 캐릭터 크기를 일관되게 유지한다. 터치 영역과 한글 UI는 실제 목표 화면에서 확인한다.
- BGM/효과음이 범위에 있으면 사용자 제스처 후 오디오 시작, 음소거, 재진입 시 중복 재생을 확인한다.
- 방치형 보상은 정의된 경과 시간·상한·효율에 따라 계산한다. 브라우저 시계만 사용하는 데모의 한계를 밝히고 실제 서비스의 서버 권한 경제를 구현한 것으로 주장하지 않는다.

## Three.js 3D

- 게임 요구와 대상 브라우저에 맞춰 렌더러를 고른다. WebGPU를 당연한 최적화로 취급하지 않고 호환성·셰이더·측정 근거로 판단한다.
- 절차 생성은 seed뿐 아니라 생성기 버전과 매개변수도 저장해야 다시 같은 세계를 만들 수 있다. 대규모 좌표에서는 카메라 상대 좌표나 원점 이동을 검토한다.
- LOD 교체는 새 지형 준비 후 수행해 공백을 방지한다. 시각 지형과 충돌 지형이 서로 다른 시점에 교체될 때 낙하/끼임을 테스트한다.
- 무거운 지형 생성은 필요할 때 워커로 분리한다. 작업 ID/세대 번호로 오래된 응답을 버리고 큐와 버퍼 전송을 측정한다.
- 우주선 등 복잡한 3D 에셋은 컨셉→여러 각도 기준→모델→최적화→게임 검증으로 진행한다. Blender 사용은 도구가 실제로 가능할 때만 수행하며 이미지 생성만으로 3D 모델을 만들었다고 말하지 않는다.
- triangle 수만 보지 말고 머티리얼/드로콜/텍스처/충돌 비용을 함께 평가한다. 장면을 나갈 때 geometry/material/texture 등 소유 자원을 해제한다.

## 보존할 경계

렌더러 교체는 시뮬레이션·저장·입력 계약과 분리하고 기존 플레이 시나리오로 회귀를 확인한다. 단순 2D 게임에는 우주 좌표계, LOD, 워커 지형 생성 같은 무관한 기술을 도입하지 않는다.
