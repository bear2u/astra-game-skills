# Astra식 게임 제작

사용자가 원하는 플레이 경험을 실행 가능한 게임으로 만들고, AI가 상태를 관찰하고 문제를 재현하며 수정 결과를 검증할 수 있게 구성한다. Astra는 이 개발 방식의 참고 사례이며 엔진이나 필수 런타임 의존성이 아니다. 특정 모델의 사용 가능 여부를 가정하지 않는다.

## 범위와 출발점

- 요청한 범위와 기존 프로젝트를 먼저 확인한다. 컨셉만 요청하면 컨셉에서, 기획서만 요청하면 기획서에서 마친다. 게임 제작 요청이면 계획만 제시하지 말고 실행 가능한 결과까지 진행한다.
- 기존 코드, 프로젝트 지침, 실행 명령, 저장 데이터와 에셋을 확인하고 재사용한다. 작은 수정 때문에 전체 스택이나 렌더러를 바꾸지 않는다.
- 플레이어가 반복하는 행동, 행동의 보상, 실패 또는 장애물, 한 판의 종료 조건을 짧게 정한다. 예: “진열하고 계산하고 번 돈으로 확장하는 편의점의 하루”.
- 대상 기기, 세로/가로 화면, 터치/키보드, 싱글/멀티플레이, 요청한 공개 배포 여부를 확인한다. 중요한 미정 사항만 질문하고 나머지는 가정을 밝혀 진행한다.
- 새 2D 브라우저 게임은 별도 선호가 없으면 Phaser + TypeScript + Vite를 우선 고려한다. 3D 공간과 카메라가 핵심이면 Three.js를 고려한다. 기존 엔진과 명시한 선택을 우선한다. 프로젝트 버전에 맞는 공식 API를 확인한다.
- 완성형 웹사이트 제작은 사용 가능한 Sites 제작 스킬과 함께 진행한다. 이미지, 스프라이트, 맵, 배포 등 전문 작업도 해당 스킬이 있으면 필요한 단계에서만 읽는다.

## 1. 플레이 경험과 시각 기준

1. 사용자의 표현을 관찰 가능한 수용 조건으로 바꾼다. “반응이 빠르다”는 입력→상태 변화 지연, “어디든 간다”는 이동 가능한 영역과 전환 조건으로 구체화한다.
2. 새 게임은 본격적인 에셋 양산 전에 이미지 생성으로 대표 플레이 화면의 컨셉을 만든다. 기존 기준 이미지가 있으면 활용한다. 팔레트, 카메라, 인물 크기, 조명, UI 밀도, 글자 가독성을 기록한다.
3. 컨셉 이미지는 실행 화면 또는 실제 스프라이트로 오인하지 않도록 구분한다. 이미지 생성이 불가능하면 그 한계를 밝히고 임시 아트 기준으로 구현을 이어간다.
4. 사용자에게 선택을 요구한 상황이 아니면 이미지 승인 대기를 필수 관문으로 만들지 않는다. 가장 적합한 방향으로 작은 프로토타입을 진행하고 피드백을 반영한다.

## 2. 작고 완결된 플레이 구현

- 먼저 한 공간·한 핵심 행동·한 보상/실패·재시작이 연결되는 최소 플레이 루프를 만든다. 방치형은 전투→보상→강화→다음 전투, 경영 게임은 입고→판매→정산처럼 연결한다.
- 시뮬레이션/규칙, 입력, 렌더링, 저장, 진단 기능의 경계를 필요한 만큼 나눈다. 단순한 게임에 거대한 프레임워크를 만들지 않는다.
- 난수 seed와 시뮬레이션 시간을 주입 가능하게 만들고, 프레임 속도가 규칙/경제 결과를 바꾸지 않게 한다. 저장이 필요하면 버전과 로드 검증을 둔다.
- 먼저 플레이 가능하게 만든 뒤 디버그 API와 재현 장면을 붙이고, 콘텐츠를 확장하기 전에 첫 검증 루프를 끝낸다.
- 2D 입력·물리·스프라이트 또는 3D LOD·워커·에셋 처리는 [엔진별 구현 기준](references/engine-patterns.md)을 필요한 부분만 읽는다.

## 3. 관찰과 재현 기능

[디버그 계약과 테스트 기준](references/debug-and-testing.md)을 읽고 프로젝트에 맞춰 구현한다.

- 개발/테스트 빌드에서 `window.__GAME_DEBUG__` 같은 버전 있는 진단 인터페이스를 제공한다. 기존 이름이 있으면 유지한다.
- JSON으로 저장 가능한 상태 스냅샷, 준비 상태, 시나리오 로드/초기화, 제한된 테스트 명령, 성능 계측을 제공한다.
- 정상 진행, 경계/실패, 문제가 생긴 상황을 직접 불러올 수 있는 seed 기반 시나리오를 만든다. 장르에 필요 없는 장면은 추가하지 않는다.
- 초기화는 이전 타이머·리스너·비동기 작업·물리 객체·난수·테스트 저장소를 정리한다. 재현을 위해 실제 사용자 저장 데이터를 삭제하지 않는다.
- 프로덕션에서는 상태 조작용 API와 테스트 진입점을 제외한다. 쿼리 문자열 하나로 공개 빌드의 조작 기능을 활성화할 수 없게 한다.

## 4. 실행 → 관찰 → 진단 → 수정 → 재검증

1. 고정된 시나리오와 seed로 실제 브라우저를 실행한다. 자산 및 게임 준비 조건을 기다린다.
2. 실제 키/터치/포인터 입력으로 핵심 행동을 수행한다. 스크린샷, 상태, 오류, 관련 성능 수치를 같은 실행에서 수집한다.
3. 증상에 대한 가설을 세우고 관련 부분을 좁혀 수정한다. 스크린샷만 보고 규칙의 정확성을 판단하거나 내부 상태만 보고 조작감을 판단하지 않는다.
4. 같은 조건으로 다시 실행해 행동 결과와 회귀 여부를 비교한다. 기존 실패 조건이나 성능 기준을 낮춰 통과시키지 않는다.
5. 핵심 진행, 저장/복원(구현된 경우), 재시작과 대상 화면 크기를 확인한다. 돈/인벤토리/보상 등 중요한 규칙에는 의미 있는 단위 테스트를 둔다.
6. 막힌 항목은 원인, 시도, 필요한 환경을 기록한다. 브라우저 실행 불가를 성공으로 바꾸거나 테스트용 상태 주입을 실제 플레이 통과로 보고하지 않는다.

성능 수정에는 비교 가능한 전후 측정값을 붙인다. 같은 기기/브라우저/뷰포트/seed/워밍업/관찰 구간을 사용하고, headless 수치를 실제 기기의 GPU FPS로 표현하지 않는다. 목표 수치는 프로젝트에 맞춰 정하며 다른 게임의 개선 수치를 목표나 보장으로 재사용하지 않는다.

## 5. 확장과 전달

- 검증된 작은 루프 위에 콘텐츠와 기능을 추가한다. 새 주요 기능마다 관련 재현 장면을 갱신한다.
- 재미, 난이도, 시각적 취향은 사용자의 플레이 피드백으로 조정한다. 자동 테스트가 재미를 입증한다고 주장하지 않는다.
- 수정에는 증상→재현 조건→원인→변경→검증 근거를 간결하게 남긴다. 작업 규모에 맞춰 프로젝트 내 실행 방법, 조작법, 시나리오 목록, 주요 검증 결과를 유지한다.
- 완료 시 플레이 방법/접근 경로, 구현 범위, 실제 실행한 검사, 남은 제한을 전달한다. 미구현 온라인 동기화나 서버 저장을 구현된 것처럼 설명하지 않는다.
- 공개 배포를 요청받았다면 해당 호스팅 스킬로 배포하고 실제 URL에서 로딩과 핵심 플레이를 확인한다. 제작 스킬을 사용했다는 이유만으로 공개 권한을 가정하지 않는다.
